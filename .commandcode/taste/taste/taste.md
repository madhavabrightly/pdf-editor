# Taste
- Expects the agent to research solutions thoroughly before implementing — consulting multiple websites, research papers, and several code repositories/code dumps (GitHub, GitLab, Gitee, etc.) — especially for hard concurrency/rendering/threading problems. Confidence: 0.8
- Expects "pro"-level, uniquely engineered solutions rather than naive/"noob" approaches. Confidence: 0.7
- Works with urgency and expects the agent to keep moving fast and autonomously rather than stalling or over-asking. Confidence: 0.5
- Expects the agent to autonomously assess leftover/in-progress work (after a session closes) and finish it in the same run, rather than stopping to ask for clarification. Confidence: 0.55
- Dislikes having to repeat instructions; expects the agent to act on previously stated requests and to remember and keep applying standing "rules" over multiple sessions. Confidence: 0.7
- Strongly rejects mock, simulated, or look-alike implementations ("no mocks... looks fake"); features must be genuinely real and functional, not a stub, a cosmetic overlay, or a trick that only appears to work. Confidence: 0.8
- Wants edits to take effect directly and in place ("on the spot"), with the result matching the document's own appearance (its real font and colour) so it reads as the actual document rather than something pasted on top. Confidence: 0.7
- Wants the editing UI itself to be visually invisible — no floating/bordered editor box or overlay chrome; the editor should be indistinguishable from the page (the document's own font, size, colour and background) so it "looks like editing the document". Confidence: 0.65
- Expects the fewest possible interaction steps: a single click should start editing anywhere on the page, without double-clicking, opening a second box, or re-clicking into another field between edits. Confidence: 0.6
- Prefers simple ▲/▼ style stepper buttons in the toolbar for numeric adjustments (e.g. line spacing) that apply live to the thing being edited. Confidence: 0.5
- Communicates in profane, insulting, high-pressure language (including self-harm rhetoric) as a way of pushing the agent; expects the agent to treat it as urgency-driven venting and keep building, staying factual and honest about results without moralizing or lecturing. Confidence: 0.55
- Holds the app to the standard of established commercial tools (e.g. Adobe Acrobat) as the bar for feature completeness and behaviour. Confidence: 0.5
- Prefers a native C++ backend for desktop applications; Node.js is acceptable only in an auxiliary/tooling role, never as the application backend. Confidence: 0.6
- Prefers shipping desktop apps as a single self-contained `.exe` (native shell hosting an HTML/web UI) rather than a bundled-runtime/installer approach. Confidence: 0.55
- Expects user-facing features to be discoverable through visible, explicit UI controls (e.g. a toolbar button) — hidden gestures like double-click, with no visible affordance, read as "there's no way to do this". Confidence: 0.6
- Expects the agent to verify a shipped feature actually works from the user's side (e.g. driving the real UI in a real browser) rather than assuming it works from the code. Confidence: 0.55
- Expects editing tools to support selecting and editing multiple items at once (e.g. dragging a box over a paragraph to edit it as a block), with the original formatting — line spacing, indentation and whitespace — preserved rather than collapsed or reflowed. Confidence: 0.5
- Expects a document page to be parsed into real, selectable objects — not just a text layer: vector geometry (lines, rules, table borders, shapes), images and shades must also be captured and individually selectable/editable. Confidence: 0.65
- Wants line spacing/leading to be user-controllable when editing text (increase or decrease the space between lines) instead of being locked to the original. Confidence: 0.6
- Expects rendering to be exact and of high quality rather than approximating the page ("exact parsing, accurate rendering"). Confidence: 0.6
- Wants true Word-like document editing ("mirrored edit"): the whole page/document should be parsed into an editable model where text changes reflow/retypeset as a unit, rather than a redraw over captured line boxes or paragraph-scoped reflow. Confidence: 0.85
- Rejects the agent declaring scope boundaries or "what I'm not going to fake" instead of building the requested capability; expects the requested feature to be implemented now, not deferred to a "next project". Confidence: 0.7
- Holds that work is only "done" when it passes real verification — compilation, unit tests, integration tests, visual regression and a save/reopen round-trip — with every claim backed by an actual test output; failing or skipped items must be stated plainly, never hidden or dressed up. Confidence: 0.8
- Expects round-trip validation for any file/serialization work: write out the result, close, reopen it, re-parse and compare against the original, rather than declaring success because the current on-screen view looks right. Confidence: 0.7
- Prefers root-cause architectural fixes over symptom patching: inspect the entire existing architecture first, produce an architecture gap report, reuse the parts that work, and replace only the fundamentally wrong abstractions. Confidence: 0.75
- Wants an ordered, phased implementation plan that builds the foundation layers (document model, layout/metrics engine, coordinate mapping) before caret/selection/UI polish. Confidence: 0.7
- Insists the authoritative document model and layout engine stay native and deterministic C++ — not a browser `contenteditable`, an HTML text overlay, or CSS used as the layout engine for the document. Confidence: 0.75
- For large implementations, expects a structured final report: architecture diagram, changed files, new files, dependencies, build instructions, test instructions, known limitations, completed and failed tests, and regression/round-trip results. Confidence: 0.7
- Treats the PDF as an import/export format, not the editing surface: clicking EDIT should convert the page into a separate, authoritative native document (a distinct view→editor mode) so the user is editing a document, not a PDF; the original PDF is only the input. Confidence: 0.6
- Requires that any PDF element which cannot be safely reconstructed be preserved as an immutable "protected visual object" rather than destroyed or approximated — visual content must never be lost just because it can't be interpreted semantically. Confidence: 0.6
- Models whitespace as real document characters rather than inferring it from pixel/glyph gaps, so inserting or removing spaces is a genuine edit to the text model. Confidence: 0.55
- Prefers the document model to store text semantically (text plus style, alignment, indentation, spacing-before/after, line-spacing, width) with a layout engine computing the resulting line positions, rather than persisting raw PDF coordinates. Confidence: 0.55
- Requires saved output to be a real PDF with searchable/selectable text (images stay images, vectors stay vectors) — never a screenshot of the rendered document. Confidence: 0.6
- Treats visual parity between the reconstructed document and the original page render as a first-class acceptance criterion: render both, compute a pixel difference against a configurable threshold, and fail the conversion (with a difference report) if it exceeds it. Confidence: 0.6
